### FIX 2 — Make the offline fallback path transparent and verify it doesn't bypass core algorithms

**What went wrong**: when Gemini/OpenRouter rate-limit or error, the system silently falls back to template-based claim generation, but the API still returns `200 OK`/`201 Created` with no indication fallback mode was used. This is a transparency problem for a project whose entire pitch is genuine LLM-driven agentic reasoning wrapped around explainable algorithms.

**Required fix**:
1. Add a `"mode": "live" | "fallback"` field to every `Turn` object returned by `/next-turn`, indicating whether that specific turn's claim was generated by the real LLM API or the offline fallback.
2. Add a corresponding small visual badge/indicator in the React UI (on each `ClaimCard`) showing which mode produced that claim — this must be visible, not hidden in dev tools/logs only.
3. Write an explicit test (`test_fallback_uses_real_algorithms.py`) that forces fallback mode (mock a 429/404 from both APIs) and asserts that `resolution.py`'s `check_contradiction()` and `mcts.py`'s `select_best_rebuttal()` are still actually invoked and still operate on real data — fallback should only ever replace the `generate_claim` language-generation step, never the contradiction-checking or move-selection logic. If the current fallback implementation bypasses either of those, fix it so it doesn't — the algorithms must always run for real, even when the LLM call itself is templated.
4. Fix the recursive string-nesting bug's root cause properly: rather than just truncating/cleaning nested opponent-claim text after the fact, restructure the fallback template so it never interpolates the opponent's full previous claim text into a new string in the first place (e.g., reference the opponent's claim by ID/summary object, not by string-embedding).
